# Phase 2.9 — Correctness Hardening (Design Spec)

**Date:** 2026-07-06
**Status:** Approved (user directive: "do all the changes and fixes")
**Source:** Two adversarially-verified review passes (17 agents, 65 findings, 64 confirmed / 1 refuted).
Full finding details live in the session transcript; this spec captures what we fix and why.

## Why this phase exists

A full-repo review found correctness bugs that make some shipped numbers wrong and would corrupt
every Phase 3 result if not fixed first:

1. **Energy conservation violation** — `engine.run` sender caps ignore the sender's own load and
   misplace the discharge-leg √η, so `step()` silently cuts promised exports while receivers keep
   full settlement credit. Round_robin's entire 30.69 kWh "advantage" on `overnight_outage_hard`
   is phantom energy; `24h_uniform`'s served=1.000 is really ≈0.972. The `haves_havenots` showcase
   cell is unaffected (verified: zero phantom — no PV, 1 kW loads, large "have" rates).
2. **Receiver caps forbid feasible transfers** — inbound energy is clipped to battery-absorption
   limits even though `step()` routes received energy straight to load (DC bypass). A full-battery
   house with unmet load has cap ≈ 0.
3. **Real-data solar shifted ~+6 h** — `fetch_data.py` requests NSRDB with `utc=true` but the sim
   reads timestamps as naive local. All `24h_resstock*` numbers (81.3 %/83.9 %, "35.7 kWh saved",
   "Gini −66 %") were computed on inverted day/night physics.
4. **TZ-dependent noise** — `NRELSolar._noise` seeds from naive `datetime.timestamp()`, so results
   differ by machine timezone (breaks the byte-identical reproducibility mandate).
5. **ResStock adapter unit/alignment bugs** — kWh→kW conversion divides by scenario `dt_hours`
   instead of the data's native 15-min interval; real ResStock timestamps are period-ENDING but
   the adapter assumes period-beginning (one-tick lag; crash at year start).
6. **LP ceiling fragility** — no curtailment slack (hard-crash on any solar-rich islanded tick;
   the LP has never been solved with nonzero solar) and no per-house send/recv bounds (ceiling not
   engine-feasible in energy-abundant regimes; verified harmless on the shipped 0.5294 ceiling).
7. **Vacuous tests** — RT-efficiency test is a tautology; Gini and round_robin (the paper's
   reference baseline) have no numeric pins; mock-LLM e2e tests exercise the YAML-fence parse path
   while live runs use the tool-use path; `observe()` clobbers the react queue (19.5 % of inbound
   REQUEST/OFFERs silently destroyed despite a "re-queued" docstring).
8. **Instrumentation gaps** — scenario `llm:` knobs silently dead; `failure_modes_active`
   hardcoded `{}`; `llm_cost_usd_estimated` hardcoded 0.0; no zero-LLM control; `run.py` has no
   `--seed`; `compare.py` clamps negative gap_closed to 0 % and can't aggregate seeds.

## Physics fixes (exact formulas)

Both caps must mirror `household.step()` exactly (see its DC-bypass model):

```
deliverable_batt_kw = min(battery_max_rate_kw, available_kwh / dt) * sqrt_eff
sender_cap_kw   = max(0, (solar_kw - load_kw) + deliverable_batt_kw + (grid_max_kw if connected else 0))

absorb_batt_kw  = min(battery_max_rate_kw, headroom_kwh / (sqrt_eff * dt))
receiver_cap_kw = max(0, load_kw - solar_kw) + absorb_batt_kw
```

Plus a strict-mode invariant after every `step()`: `achieved_net_export_kw == desired` (tol 1e-9).
This is the assert that would have caught bug #1 on day one.

LP additions (pure relaxations, so LP stays an upper bound):
- `curt` variable per (house, tick), coefficient −1 in the power balance, zero objective cost —
  mirrors the engine's wasted-energy semantics.
- Per-tick bounds: `send ≤ min(bus, solar + rate·√η + grid_if_connected)`,
  `recv ≤ min(bus, load + rate)`.
